# Architecture & Data Model

## Status: this file describes the TARGET architecture, not the current prototype
The existing `gig-request-prototype.html` (single-file artifact using `window.storage`) was a valuable first pass to validate the interaction design, but the real build described below is a genuine step up in scope — a real backend, real storage, and real hosting. Treat the prototype as a reference for interaction patterns (tip-weighted queue, scarcity messaging, dedication-style notes, etc.), not as the architecture going forward.

## Domains and URL structure (multi-tenant from the start)
- **`bribetheband.live` (root) is a marketing/landing page**, not Travis's personal crowd page. It explains the product, links to performer login, and links to `signup.html` (see Self-service signup below). **Currently just a placeholder** — real landing page content is deliberately deferred until the product itself is working end-to-end for Travis; his own page is being used as the de facto testing area in the meantime.
- **`bribetheband.live/{handle}` is the crowd-facing request page**, one per performer — e.g. `bribetheband.live/travis-ross`. This is the link/QR code a performer would actually share from stage. Publicly accessible, no login.
- **`bribetheband.live/console.html` is the authenticated Performer Console** (see below) — setlist building, gig control, request queue, song catalog management. Not yet given a clean URL (e.g. `/console`); works fine as-is for now.
- **`bribetheband.live/viewer.html` is the swipeable Chart Viewer** (Stage 2 — see The three surfaces below), including its live request drawer. Opens in its own browser tab from the console's "Start the Set" button, rather than navigating within the console tab, so the performer can get back to the console without losing their place.
- **`bribetheband.live/signup.html` (also reachable as `/signup`) is the self-service signup page** — see Self-service signup below. New performer accounts are no longer created manually by default.
- **Routing implementation:** the site is still a plain static deploy — a `vercel.json` rewrite rule sends any single-segment path that isn't a real file (e.g. `/travis-ross`) to `request.html`, which reads the handle from `window.location.pathname` rather than a query parameter. Real files (`console.html`, `viewer.html`, `signup.html`, `manifest.json`, the root `index.html`) are served directly and never hit the rewrite, since Vercel checks the filesystem before applying rewrites. An explicit `{"source": "/signup", "destination": "/signup.html"}` rewrite was added ahead of the generic `/:handle` catch-all (order matters — first match wins) so the clean, shareable `bribetheband.live/signup` URL works for affiliate links without falling through to the handle-lookup rewrite.
- **The site now includes several Vercel serverless functions** under `/api`: `wasabi-upload-url.js` (issue a presigned upload URL), `wasabi-delete-chart.js` (delete a chart PDF), and (used once, then removed from the UI) `migrate-legacy-charts.js` (one-time folder-naming cleanup — see Chart storage below, including a real bug it had). A root-level `package.json` declares their shared dependencies (`@aws-sdk/client-s3`, `@aws-sdk/s3-request-presigner`, `@supabase/supabase-js`) so Vercel installs them at build time.
- **`travisrossmusic.com` — a separate, simple static companion site.** Bio, music samples, contact info, gig calendar. No database, no backend of its own. Links (and later carries an embed widget) to Travis's `bribetheband.live/travis-ross` page. Not a staging ground for the app itself.
- **Both domains registered through Namecheap.**
- **Rejected approach:** building the request app on `travisrossmusic.com` first, then migrating to `bribetheband.live`. Migrating a live app between domains means redoing auth/cookie config, Stripe webhook URLs, hosting DNS, and CORS — real rework for no benefit.
- **V2 "install on a band's page" widget, clarified:** the app does not run on each performer's own domain. Every performer gets a hosted page at `bribetheband.live/{their-handle}`, and the "widget" other sites install is a small embeddable snippet (button/card) linking or lightly iframing to that hosted page.

## Performer handle rules
- **Unique, enforced at the database level** — `performers.handle` already has a unique constraint.
- **Format validation, now actually enforced in `signup.html`**: lowercase letters, numbers, and hyphens only, at least 3 characters, live-checked against existing handles as the performer types (a plain `select` against the already-public `performers.handle` column) — since it goes directly into a URL path.
- **Reserved words are blocked in `signup.html`** so a performer can't claim a handle that collides with the app's own routes: `console`, `console.html`, `viewer`, `viewer.html`, `login`, `admin`, `api`, `request`, `request.html`, `index.html`, `manifest.json`, `www`, `signup`, `signup.html`. (`signup`/`signup.html` were added to this list when the signup page itself was built.)
- **"Set once" is a V1 UI/product decision, not a hard technical constraint.** The identity model (internal ID vs. handle, see below) already means the handle can technically change later without breaking anything, since storage and DB relationships point at the immutable internal ID — this is also why chart storage keys off the immutable ID rather than the handle (see Chart storage below). Restricting handle editing to a one-time set (no "change my handle" UI exists) is just a simplification, not a permanent limitation.
- **A rare race condition is accepted, not specially handled**: two people grabbing the same handle at nearly the same instant could both pass the live-check before either finishes signing up. If that happens, the loser's `performers` insert (via the signup trigger — see below) fails on the unique constraint, leaving them with an auth login but no performer profile — the same "logged in but no performer profile is linked to this account" state `console.html` already detects and reports clearly. Not a new failure mode; just confirmed the existing one covers it.

## Backend & hosting
- **Backend/database: Supabase.** Real relational Postgres database. Built-in auth (email/password) is used for real performer login — see Performer Console below. Free tier comfortably covers this scale. (No realtime subscriptions are actually wired up yet, despite earlier notes assuming they would be — the live request drawer uses polling instead; see Chart Viewer below.)
- **Static/app hosting + serverless functions: Vercel.** Git-push-to-deploy, trivial custom-domain connection, and now also hosts a small set of serverless functions (see Domains above) for secure PDF upload/delete/migration. `bribetheband.live` is live and DNS-confirmed (A record `@` → `76.76.21.21`, CNAME `www` → `cname.vercel-dns.com`).
- **Chart storage stays on Wasabi** (see below) — the app can now write to and delete from it directly (not just read).
- Real payments (Stripe) add no monthly fee, just a per-transaction cut, whenever that integration is built.

## The three surfaces

Audience browses songs by title + artist, submits requests with optional tips, or leaves a tip with no request attached. No keys, no chart links shown — performer-only info. Fully public, no login. Now also grays out and blocks requesting any song that's hit its nightly request cap (see Request-count tracking & nightly request cap below). **Built and live.**
2. **Performer Console + Chart Viewer** — real Supabase Auth login, responsive enough to use on iPad *or* desktop. Now two separate pages rather than one toggling app (see below):
   - **Console (`console.html`, planning):** build/save/recall named setlists from the song database, see the incoming request queue (tip-ranked, with key + chart link, and a "Dismiss" action), set tonight's single request cap (and reset it mid-gig if needed) in the "Tonight's Gig" section, manage the full song catalog (add, bulk add, edit, replace chart, delete), and now a Reporting tab (see below). **Stage 1 built.** Per Travis's explicit clarification, the console is a planning/prep tool only — he does not go back to it during a live performance, so all accept/decline/splicing must live entirely in the viewer (which it now does).
   - **Viewer (`viewer.html`, performing):** the swipeable, linear page-stream chart viewer, plus the live request drawer — the only surface used during an actual performance.    - Originally designed as a single app with a mode toggle; built instead as two separate static pages linked by "Start the Set" / "Exit to Console" — simpler given the site has no framework/build step, and avoids needing complex in-page state handoff. Functionally equivalent from the performer's perspective.
3. **iPhone** — not an app at all. Its only job (when needed) is providing a WiFi hotspot so the console/viewer device has internet at venues without reliable WiFi.

## Request-count tracking & nightly request cap — built, replacing the earlier swipe/play-based design, and twice redesigned since
**This is a genuine reversal of an earlier decision**, not an addition, and it went through two rounds of correction before landing where it is now. Swipe-based play tracking (crossing forward past a song's last page recorded a "play" in a `song_plays` table) was built first, but Travis found a real flaw: flipping forward to preview upcoming songs, then going back, inflated the count with no way to tell "previewing" apart from "actually performing." The whole approach was replaced with something that has no ambiguity at all: **counting requests, not performances.**
- **`recordPlay()` and its call sites have been removed from `viewer.html`'s `goToIndex()`.** The `song_plays` table still exists in the database but nothing writes to it anymore — it's inert, not actively cleaned up (harmless to leave, since nothing reads it either).
- **Cap design, round 1 (superseded): per-song, fixed forever.** `songs.max_requests_per_gig`, set once in Manage Songs, silently reused every night. Travis caught this the moment he went looking for the field in the console. **Column dropped 2026-08-19** — see Data model below.
- **Cap design, round 2 (also superseded): per-song, per-gig.** Moved to `gig_sessions.song_caps` (a jsonb map of `song_id → integer cap`), edited from a list of every song in tonight's setlist. Travis tried this and said it added too much granularity to manage live. **Column dropped 2026-08-19** — see Data model below.
- **Cap design, round 3 (current): ONE number for the whole gig.** `gig_sessions.request_cap` (nullable integer) applies the same limit to every song in that gig — Travis's words: "Just say a song can only be requested twice and that's the limit for all songs played at that gig that night." Set from a single "Max requests per song" box in the console's "Tonight's Gig" section, right below "Start New Gig." Carries forward automatically from the previous gig (so it doesn't need re-entering every night), editable any time.
- **Mid-gig reset, built alongside round 3**: Travis also asked for "a button... which takes them all back to zero" without ending the gig (ending would lose the running order and request queue). Added `gig_sessions.cap_reset_at` (nullable timestamptz) plus a "Reset Request Counts" console button — resetting sets `cap_reset_at = now()`, and the enforcement function (below) only counts requests created after that timestamp. No request rows are touched or deleted; the reset is purely a "start counting from here" marker.
- **Cap counting is deduped by "occasion," confirmed by Travis, unchanged across all three rounds**: multiple people requesting the same song at (essentially) the same time count as one occasion toward the cap, since the performer only plays the song once for all of them — his words: "if a song is requested by 4 people and is pending, that counts as 1 request... it would still only count as one request since I'm only going to play the song once for all four people." Concretely: an occasion is either (a) a batch of accepted requests for that song sharing the same `spliced_at` timestamp (see Runtime setlist splicing below — `spliceAcceptedRequests()` groups by `song_id` and stamps every row in a group with one shared timestamp), or (b) one open, not-yet-resolved request currently pending/accepted-unspliced.
- **Enforcement happens on the crowd page**, not the console or viewer: a `get_song_request_status(p_gig_session_id)` `SECURITY DEFINER` Postgres function (see Data model / RLS below) returns each song's occasion count, the gig's cap (the same value for every song, now), and whether it's capped. `request.html` calls this after loading the active gig, again every 30 seconds, and once more immediately before actually submitting (a last-second safety check). A capped song's row is grayed out, its click handler removed, and it shows an inline "Already requested plenty tonight — try another! 🎶" note instead of the request arrow — matching Travis's ask for "graying out the button and a message... something cute." **No code changes were needed in `request.html` across any of the three cap redesigns** — it only ever consumes the function's four-column output, never reads the underlying cap storage directly.
- **The viewer keeps its own separate, simpler, non-deduped badge** — Travis's words: "let's have it track how many times the song has been requested. But this number would be the total times it's been requested, not combined like the audience request page summarizes them." This is purely informational for the performer, distinct from the cap-enforcement number: `loadRequestCounts()` (replacing the old `loadExistingPlayCounts()`) counts every individual `pending`/`accepted` request row for a song, undeduped, and the header badge reads "**requested Nx tonight**" (was "played Nx tonight"). Refreshed on the same page-turn/interval trigger as the request-drawer check. Unaffected by any of the cap-scope changes. Excludes manually-added (`is_manual`) rows — see the manual-insert feature below.
- **Why a SECURITY DEFINER function instead of relaxing RLS or a serverless function**: the crowd page is anonymous and must never be able to read raw `requests` rows (they contain tips and notes that aren't meant to be public), so straightforwardly granting `select` on `requests` was never an option. A Postgres function owned by a privileged role, marked `security definer`, can read the underlying tables internally while only ever returning the four aggregate columns declared in its signature (`song_id, requests_used, max_requests_per_gig, is_capped`) — `grant execute` (not `select`) is given to `anon`/`authenticated`. This avoids needing a new Vercel serverless function (and a service-role key) just to expose one aggregate. This same SECURITY DEFINER pattern is reused for `validate_promo_code()` and the signup-account-creation trigger — see Self-service signup below.
- **SQL migrations delivered, in order**: `migration-request-cap.sql` (v1 — `songs.max_requests_per_gig`, the `spliced_at` backfill, the original song-scoped function; hit a real Postgres return-type-mismatch error on first run — see the SECURITY DEFINER section below), `migration-request-cap-v2.sql` (v2 — `gig_sessions.song_caps jsonb`, function reads the cap from the gig instead of the song), `migration-request-cap-v3.sql` (v3 — `gig_sessions.request_cap` + `cap_reset_at`, function applies one cap to every song in the gig and ignores requests created before the reset point), `migration-manual-add-v1.sql` (v4 — excludes `is_manual` rows from the count), `migration-drop-legacy-columns-v1.sql` (drops the two now-unused columns from v1/v2 — see Data model below).
- **Scoping choice, not yet confirmed with Travis**: "Add a Song" does not have any cap field — caps are purely a per-gig setting now, with nothing to configure at the song level.

## Crowd-facing "in set / already played" indicators — separate idea, still not built
A different, smaller idea than the request cap above: showing something like "in tonight's set" on songs that are part of the current setlist. This was previously going to be powered by `song_plays`/play-limit data; since that whole approach was retired (see above), this indicator has no current data source and remains unbuilt and unscoped.

## Request flow — the live drawer, splicing, and Dismiss/Decline — built, then a real bug fixed
The full design from earlier sessions (count-only banner, performer opens on their own timing, stays open, accepted songs queue as the next swipes) is built in `viewer.html`, entirely self-contained there since Travis will not go back to the console mid-performance:
- **Notification badge**: a small 🔔-plus-count button, fixed on screen independent of the header/footer chrome (so it's visible even while that chrome is auto-hidden, or on the end-of-set screen). Shows a count only — no request detail until opened. Hidden entirely when the pending count is 0.
- **Refresh model: a page-turn check plus a background safety-net poll, not realtime.** Every `goToIndex()` call (i.e. every page turn, which is naturally when the performer is already glancing at the screen) fires a cheap, fire-and-forget `refreshPendingRequests()` — this is the primary way new requests get noticed, at effectively no extra cost since it rides along with an action already happening. A `setInterval` also runs every 45 seconds as a backup (`REQUEST_POLL_MS`), in case the performer lingers on one page for a long song and never triggers the per-page-turn check. Confirmed still correct and working as designed after a real gig — Travis asked whether the interval had changed when the bell felt slower to update, and it hadn't; the 45s figure is unchanged, it's just a backup behind the page-turn trigger.
- **Real bug found and fixed: silent query failure via FK-embedding.** The first version of `refreshPendingRequests()`/`spliceAcceptedRequests()` used Supabase's foreign-key embedding shorthand (`.select('...songs(...)')`) to pull each request's song details in one query. That shorthand depends on PostgREST recognizing an actual foreign-key relationship between `requests.song_id` and `songs.id` — which isn't reliably configured in this schema (the console's own request queue avoids the same shorthand for the same reason, doing a separate lookup instead). The embedded query errored out on every call; the error was logged to the console but swallowed otherwise, so the badge simply never appeared and nothing looked broken to the user — Travis tested a real request end-to-end (submitted from the crowd page, checked the viewer, checked the console) and correctly reported "didn't see anything," which is what led to finding this. **Fixed** by querying `requests` and `songs` separately and joining them in JavaScript (`fetchSongsByIds()`), the same pattern the console already uses.
- **Drawer**: tapping the badge opens a bottom-sheet-style panel listing every pending request, tip-ranked (same ordering as the console's queue: tip amount descending, then oldest first). Each row shows the song's key, note, tip, and a chart link; a request with no song attached (a pure tip) shows a single "Got it" button instead of Accept/Decline. The drawer stays open until the performer taps "Done" — closing it does not happen by tapping outside, a deliberate choice to avoid an accidental close mid-decision during a live set.
- **Accept**: marks the request `status = 'accepted'` immediately, but does NOT yet insert it into the page stream — see Runtime setlist splicing below for why that's deferred to drawer-close.
- **Decline**: marks the request `status = 'declined'`.
- **Got it (tip-only)**: marks `status = 'accepted'` and immediately sets `spliced_at` too, since there's nothing to splice — closes the row out in one step.
- **Console's "Dismiss" now sets `status = 'declined'`**, not `'accepted'` as it originally did — this was a real fix, not just semantics; see the explicit writeup right below.
- **Why the status value had to change**: the console's Dismiss button originally set a request's status to `'accepted'` purely to remove it from the pending list — nothing downstream ever read that value, so the mismatch between the label ("Dismiss") and the underlying value (`'accepted'`) didn't matter. Now that the viewer's drawer treats `'accepted'` as "splice this into the running order," a console Dismiss would have accidentally queued the song to play if left unchanged. Fixed by having Dismiss set `'declined'` instead, and adding a `requests.spliced_at` column (see Data model below) so splicing logic can distinguish "genuinely accepted, not yet spliced" from "already handled." A one-time backfill (`update requests set spliced_at = now() where status = 'accepted' and spliced_at is null`) was needed to mark all pre-existing `'accepted'` rows (which, under the old meaning, just meant "previously dismissed") as already closed out, so they don't get retroactively spliced into a currently-active gig the first time this code runs.

## Runtime setlist splicing — built, now with per-song dedup, and a real multi-song ordering bug fixed
The saved setlist is a template; accepted requests insert into the live gig's actual running order without modifying it.
- **Deferred to drawer-close, not immediate on Accept**: `spliceAcceptedRequests()` runs when the performer taps "Done" on the drawer, not the instant they tap Accept. It queries every request for this gig with `status = 'accepted' AND spliced_at IS NULL`, ordered by `created_at` ascending (a proxy for acceptance order, since there's no separate `accepted_at` timestamp — good enough for the expected volume of in-set requests).
- **Deduped by song**: rows are grouped by `song_id` before splicing. If several people requested (and got accepted for) the same song, the chart is loaded and inserted into `pageStream` exactly once — not once per requester — matching Travis's "I'm only going to play the song once for all four people." Every row in that group is stamped with the *same* `spliced_at` timestamp (computed once per group, not per row), which is what lets the request-cap counting (see above) treat the whole batch as one occasion.
- **Insertion point**: each unique accepted song's full chart (all its PDF pages, loaded via `pdf.js` the same way `buildPageStream()` does, including the same inline-error handling for a chart that fails to load) is spliced into `pageStream` immediately after the page currently on screen — so it becomes the very next swipe, not appended to the tail of the whole set. Multiple accepted songs in one drawer session are inserted consecutively in acceptance order.
- **Persisted for reload-safety**: after splicing, the new `orderedSongs` order is written back to `gig_sessions.runtime_order`, so the updated running order survives a page reload (not just held in memory).
- **End-of-set resume**: if the set had already reached its end screen when new songs get accepted, closing the drawer un-ends it — hides the end screen, restores the normal viewer chrome, and advances into the newly spliced song — rather than leaving the performer stuck on the end screen with new songs silently waiting.
- **Confirmation toast**: a small toast ("Added to the set: <titles> — up next") confirms what got spliced in; a song requested by more than one person shows a "(x2 requests)"-style suffix so the performer knows it was a multi-request add, since it still only appears once in the stream.
- **Known minor limitation**: the insertion position within `orderedSongs` (used only for the "Song X of Y" display count, not for actual navigation) is found via `orderedSongs.findIndex()` on the current song's id — if that song appears more than once in the set (e.g. because an earlier request for the same song was already spliced in), the count display could be very slightly off. `pageStream` itself (the actual source of truth for navigation) is never affected by this.
- **Real bug found and fixed: multi-song batches could splice backwards on a Follower.** When accepting two-or-more requests at once, every song's `requests` row was stamped with the SAME `splice_after_song_id`/`splice_after_page_num` — the pre-batch reference point, captured once before the loop over songs. This is harmless if a Follower processes the whole batch in one `checkForFollowerSplices()` call, but Realtime fires once per database write, and inserting a song involves an async chart-load in between — so in practice a Follower often received each song as a SEPARATE sync event. When that happened, the second song's stamped reference still pointed at the ORIGINAL pre-batch position (not "after song 1"), so the Follower inserted it back at that same original spot — landing it ahead of song 1 instead of after it, reversing the order from what the Master actually showed. Travis caught this live: "It did them out of order backwards because I hadn't selected 'yes, go ahead and play a song on master yet.'" **Fixed** by advancing the stamped reference point after each song in the loop — song 2's reference becomes "song 1, last page" rather than staying at the original pre-batch position — so each group's stamp is self-sufficient and correct regardless of whether a Follower processes the batch together or across separate sync events.

## Request-info box on swipe-arrival — built
Travis's ask, verbatim: "when splicing new requests would be a box/drawer that says it's a request, shows the dollar amount and the note for each request. And if I accept 2 or 3 requests at the same time, that message shows on each subsequent swipe to the new song for that request only. Only show notes and dollar amounts for the requested song swiped to and only the first time (so if I swipe backward later, don't show it again.) Make the box have a button to dismiss/close so I can swipe to the request, take a minute to say thanks for the tip and say who it's for, then close the box and play the song." Distinct from the pending-requests drawer above (which is for accept/decline decisions, before splicing) — this is a separate, centered overlay that appears automatically the first time the performer actually arrives at a spliced-in song.
- **Data now carried on the page-stream entry itself**: `spliceAcceptedRequests()`'s select query was extended from `id, song_id` to `id, song_id, tip_amount, note`, so each accepted row's tip and note are available at splice time, not just its id.
- **`requestInfo` and `requestInfoShown` attached at splice time**: for each unique spliced-in song, `requestInfo` is an array of `{ tipAmount, note }` — one entry per accepted row for that song (so 3 simultaneous requests for the same song produce 3 lines) — attached only to that song's *first* page-stream entry (`p === 1`), since that's the one the performer actually swipes onto first. `requestInfoShown` starts `false` on that entry.
- **Show-once, direction-independent mechanism**: `renderCurrentPage()` checks `entry.requestInfo && entry.requestInfo.length && !entry.requestInfoShown` right after its null-guard (before anything else, so it fires even for a song whose chart failed to load) — if true, it shows the box and flips `requestInfoShown` to `true` on that same object. Because `pageStream` entries are stable JS object references that don't get recreated on navigation, flipping the flag directly on the entry means the box shows exactly once, the first time that page is reached, regardless of forward/backward swipe direction afterward — no separate "seen" set or persisted state needed, the same pattern already used elsewhere in the page-stream design.
- **UI is a centered modal overlay, not the bottom-sheet drawer**: `#request-info-overlay` (fixed, centered, `z-index: 50`) containing a `.request-info-card` — title ("🎤 "<song>" was requested"), a sub-line (singular "Say thanks, then close this to play it." vs. plural "N requests for this song tonight — say thanks, then close this to play it." when `requestInfo.length > 1`), one `.request-info-line` per request row (note text, or an italic "No note left" placeholder if blank, plus the tip amount if any), and a single full-width "Got it — play the song" button that just hides the overlay. Nothing else pauses or changes — the performer can take as long as they want before dismissing it. This same overlay DOM is now also reused by the manual-add feature's box (see below) — the button label is explicitly reset each time either box opens, so text never bleeds between the two.
- **Tip formatting**: a small `formatTip()` helper wraps the value in `Number(...)` before formatting (matching the existing "requested Nx tonight"-style `Number(r.tip_amount).toFixed(0)` convention already used elsewhere in `viewer.html`, since Supabase/PostgREST can return a `numeric` column as a JS string) — shows nothing if the tip is zero/blank, otherwise a `$`-prefixed amount, whole-dollar or with cents only when the amount isn't a whole number.
- **Confirmed working on real hardware**, including the follow-on discovery that Followers seeing the same box (see Multi-tablet band sync below) is a real feature, not just a harmless default.

## Swipe/tap navigation: linear page-stream model — built, gesture model refined for cross-tablet reliability
Charts are NOT bounded by song when navigating — the whole set is one continuous page stream, built once at viewer load from the gig's `runtime_order` (all of a song's PDF pages in sequence, then the next song's pages, etc.), and extended live by the request drawer's splicing (see above). Rendering is done page-by-page with `pdf.js` (loaded via CDN, `cdnjs.cloudflare.com/ajax/libs/pdf.js/3.11.174`) onto a canvas, scaled to fit the viewport. A song whose chart PDF fails to load shows an inline error for just that song (title + the failed URL) rather than blocking the whole set — the performer can still click past it.
- **Input model, by pointer type** (implemented via the standard, cross-browser Pointer Events API — not anything iOS-specific, so it behaves the same on Android tablets, Surface, etc., not just iPad): a single `pointerdown`/`pointerup` pair on `#stage` branches on `event.pointerType`.
  - **Touch or pen (any tablet):** a horizontal swipe (past a small distance threshold, and clearly more horizontal than vertical) turns the page in that direction, from *anywhere* on the screen — not just a specific tap zone. A touch that barely moves (a tap) toggles the header/footer chrome, also from anywhere on the screen. This directly matches how a book app behaves.
  - **Mouse (desktop):** unchanged from the original click-zone design — clicking the left ~45% of the screen goes back a page, the right ~45% advances, and the small ~10% gap in the middle toggles the chrome. Kept mouse-specific because a mouse has hover affordance (the fading arrow icons) and doesn't need a large forgiving touch target the way a finger does.
  - A genuinely ambiguous gesture (a short diagonal drag that's neither a clean horizontal swipe nor a still tap) is deliberately ignored, so it can't misfire an unintended page turn.
  - `#stage` sets `touch-action: none` so the browser's own pan/zoom/edge-swipe-back gestures don't compete with this handling — important on tablets where an edge swipe can otherwise trigger the browser's own back/forward navigation instead of a page turn.
  - Arrow keys (← / →) still work for desktop keyboard navigation, unaffected by this change.
  - Implemented generically with no Apple-specific API anywhere in the gesture logic, so the same code path should run identically on Android tablets, Surface-type devices, etc. — not yet hands-on tested by Travis on non-Apple hardware.

## Console tabs — built
The console's sections were reorganized behind a simple tab bar rather than one long scroll: **Tonight** (Tonight's Gig incl. the request-cap panel, and Incoming Requests), **Setlists** (Build a Setlist, Saved Setlists), **Song Library** (Add a Song, Bulk Add from PDFs, Manage Songs), and **Reporting** (a range filter, Lifetime Totals, By Gig — see below). ## Reporting tab — built, now with a date-range filter
Travis's ask, verbatim: "a tally of songs requested by gig/date and then an account total." Lives in the console's own **Reporting** tab (not the viewer — this is a between-shows need, not a live-performance one), lazily loaded the first time that tab is opened (rather than on every login) since it's not needed during setup or a show.
- **No schema changes needed** — everything is aggregated client-side from data already being written: `gig_sessions` (`id`, `gig_code`, `status`, `created_at`) and `requests` (`gig_session_id`, `song_id`, `tip_amount`, `status`, `is_manual`), both already scoped to the logged-in performer via existing RLS policies.
- **Manually-added songs excluded entirely** (`is_manual = true` rows are filtered out of the request query) — same reasoning as the crowd-facing cap and the viewer's own request badge: a manual add isn't a real crowd request and never collected a tip, so counting it here would inflate both the request tally and the tip total.
- **Date-range filter, built alongside the initial version**: a "Reporting Range" control (All time / Last 30 days / Last 90 days / Last 365 days / Custom range) filters both sections below it by each gig's date (`gig_sessions.created_at`). Fetches the performer's full gig + request history exactly once per Reporting-tab visit, then every range switch is a pure in-memory filter and re-render — no extra round trip to Supabase for flipping between presets. The section heading ("Totals — Last 30 Days," etc.) always reflects the active range so it's never ambiguous what's being shown.
  - **Deliberately left out: a built-in period-vs-previous-period comparison** (e.g. "last 30 days vs. the 30 before that"). Custom range already covers this manually (run it twice), and a built-in version adds real complexity — choosing/aligning a comparison window, handling a partial current period — for a need that hasn't come up yet. Worth adding later if Travis finds himself doing that comparison by hand often; deliberately not built preemptively.
- **Lifetime Totals section** (title changes to match the selected range, e.g. "Totals — Last 90 Days"): total tips collected, total song requests (song-attached rows), total tip-only submissions (no song attached), and total gigs run within the range — four stat tiles — plus a "Most-Requested Songs" list (top 10, by request count then tip total) for that range.
- **By Gig section**: every gig within the range (active and ended), most recent first, each showing its date, live/ended status, gig code, a per-gig request count + tip total, and an inline per-song breakdown table (song, times requested that gig, tips for that song that gig).
- **Counting choice, deliberately simple, not deduped by "occasion"**: unlike the crowd-facing cap (which dedupes simultaneous requests for the same song into one "occasion" — see Request-count tracking above), the reporting tally counts every individual non-manual request row, matching the viewer's own "requested Nx tonight" badge convention rather than the cap's dedup logic. This means a song requested by 4 people at once shows as "4 requests" here (and "4 tips"), even though the performer only played it once — that's intentional, since this is a earnings/popularity report, not a request-limit calculation, and Travis would want to see all 4 tips reflected in his tip total.
- **Tips counted regardless of accept/decline status**: `tip_amount` is set at submission time, before any accept/decline decision, and in this app's model a tip is treated as collected once submitted (no refund flow exists) — so the tip total includes declined requests' tips too, not just accepted ones. Worth revisiting once real Stripe payments exist, if a declined request should ever trigger an actual refund.

## Multi-tablet band sync — built, confirmed working on real hardware (with one bug found and fixed since)
For a full band running the viewer on 4-6 tablets sharing one login (rather than Travis's original one-performer-one-device setup), the design (Travis's own proposal) is: tablets navigate independently most of the time, but converge briefly the instant a request is accepted, so every tablet's underlying song order stays identical going forward. No new account type or signup branching — Master/Follower is a per-device choice made every time a tablet opens the viewer, not an account-level setting, so a solo performer's experience is completely unaffected by any of this.
- **Role selection**: `viewer.html` reads `?role=follower` from its URL query string (default `master`). The console's "Tonight's Gig" panel has a **"Join as Follower"** button next to "Start the Set" (shown once a gig has a running set) that opens `viewer.html?role=follower` in a new tab — meant for a bandmate's own tablet, same shared Supabase Auth login as the Master.
- **Master**: unchanged viewer behavior (request drawer, accept/decline, splicing), plus `spliceAcceptedRequests()` also stamps two new columns — `requests.splice_after_song_id` / `requests.splice_after_page_num` — onto every row in a drawer-close batch, recording which song+page the Master was viewing when it spliced each song. See the multi-song ordering bug fix in Runtime setlist splicing above — this reference point now advances per song within a batch, not just once for the whole batch.
- **Follower**: no request-drawer UI at all — the badge stays permanently hidden and its click handler no-ops — with a small "👥 Following" indicator shown in the header instead. Subscribes to **Supabase Realtime** (Postgres Changes) on the `requests` table filtered to the active `gig_session_id` — the first use of Realtime anywhere in this app; everything before this was either polling or one-shot queries — with a 15-second poll (`checkForFollowerSplices()`) kept only as a backup for a missed/reconnecting realtime event, not the primary mechanism (the whole point of using Realtime here is that a Follower's screen should react in about a second, not wait out a poll interval, since this is meant to be visibly happening live on stage).
- **Sync mechanics**: on a new splice, `checkForFollowerSplices()` groups newly-spliced rows by `spliced_at` (the Master already stamps one shared timestamp per song when splicing — see the Request-count tracking section — so grouping by it here reconstructs the same per-song batches in the same order the Master processed them). For the first group in a batch, it locates the matching song+page in its own local `pageStream` using the stamped reference columns, jumps `currentIndex` there, and inserts the new song immediately after — using a shared `insertSongAtIndex(song, extra, insertAt, songInsertAt)` helper extracted from `spliceAcceptedRequests()`, so both the Master's own splice and a Follower's mirrored splice build identical page-stream entries (same chart-load/error handling, same show-once overlay wiring — meaning Followers get the same dismissible tip/note box the Master sees, by default, since it's harmless/informative and comes for free from sharing the same insertion code). Subsequent songs in the same batch build on top of that same insertion point, exactly mirroring the Master's own loop.
- **Fallback for a divergence that shouldn't normally happen**: if a Follower can't find its local copy of the Master's reference song+page (every tablet is expected to process the same splices in the same order, so this would indicate some kind of desync), it logs a console warning and inserts the new song at the end of its own set rather than silently dropping it.
- **New SQL**: `migration-band-sync-v1.sql` — the two new `requests` columns, plus enabling the `requests` table on the `supabase_realtime` publication (wrapped in an idempotent existence check via `pg_publication_tables`, so it's safe to re-run).
- **Confirmed working on the first real-hardware test**: Travis ran Master on a tablet and Follower on a desktop, moved the Follower ahead independently, accepted a crowd-page request on the Master, and watched the Follower converge to the Master's exact page before the new song appeared for both — matching the design with no bugs found. He also confirmed Followers seeing the request-info tip/note box is the right call (not just a harmless default) — it helps band members see what they're earning and confirms they're looking at the actual requested song.
- **Real bug found on the SECOND hands-on test, since fixed**: accepting two requests at once, on a real gig, spliced them backwards on a Follower tablet. Root cause and fix are described in Runtime setlist splicing above.

## Master-only "search & manually insert a song" tool — built, confirmed working on real hardware
Travis's son's suggestion: a search-the-catalog tool on the viewer for pulling in a song that isn't part of tonight's planned setlist or a crowd request — same real-time, filter-as-you-type UX as the console's setlist search (across title, artist, key). Master-only, for the same reason the request drawer is Master-only: avoids two people independently adding songs from different tablets at once.
- **New header button, "🔍 Add Song"**, visible only for `role === 'master'`. Opens a search overlay that lazily loads the performer's *entire* song catalog on first use (not just tonight's `runtime_order` — the whole point is pulling in something unplanned) and filters live against title/artist/`song_key`/`key_with_capo` as the Master types.
- **Confirm/Dismiss flow**: tapping a search result opens a small confirm dialog ("Display this song?"). Dismiss closes both dialogs with no change at all. Confirm calls `insertManualSong(song)`.
- **Reuses the band-sync pipeline entirely — no new sync mechanism**: `insertManualSong()` inserts the chart locally via the same `insertSongAtIndex()` helper used everywhere else, persists `gig_sessions.runtime_order`, and inserts a row into `requests` tagged `is_manual: true` (`status: 'accepted'`, `spliced_at` set immediately, the same `splice_after_song_id`/`splice_after_page_num` reference columns the Master stamps for a real accepted request). Every Follower tablet picks this up through the exact same Realtime subscription + `checkForFollowerSplices()` path built for crowd requests — `checkForFollowerSplices()` was extended to read `is_manual` per row and pass `{ manualAdd: true }` instead of `{ requestInfo }` to `insertSongAtIndex()` when mirroring one.
- **`insertSongAtIndex()` signature changed** from a raw `requestInfo` array to a generic `extra` options object (`{ requestInfo }` or `{ manualAdd: true }`), since a page-stream entry now needs to carry one of two mutually exclusive show-once flags: `requestInfo`/`requestInfoShown` (crowd request — see above) or `manualAdd`/`manualAddShown` (this feature). `renderCurrentPage()` checks `requestInfo` first, falling back to `manualAdd`, so exactly one dismissible box (if either) ever shows per entry.
- **Distinct swipe-arrival box**: reuses the same `#request-info-overlay` DOM (only one of the two box types is ever showing at once) via a new `showManualAddBox()` function — different title/sub copy ("🎸 '<title>' was manually added" / "Dismiss and rock on! 🤘"), no tip/note lines, and the shared close button's label is set fresh each time a box opens (`showRequestInfoBox()` now also explicitly resets it) so the two box types never bleed into each other's button text.
- **Excluded from crowd-facing cap counting, the viewer's own badge, and reporting**: a manually-added song is not a crowd request and must never trip that song's nightly request cap or inflate its tally. `migration-manual-add-v1.sql` adds `requests.is_manual` (default `false`) and replaces `get_song_request_status()` (v4, same signature as v1-v3) to filter out `is_manual` rows from the occasion count. `loadRequestCounts()` (the "requested Nx tonight" header badge) and the console's Reporting tab (see above) were also updated to skip `is_manual` rows for the same reason.
- **Confirmed working on real hardware**: "worked perfectly" — Travis flagged encores and unplanned crowd shout-outs (e.g. someone yelling for a song that isn't on the setlist) as the exact use case this covers.

## Self-service signup — Phase 1 built (free accounts only; billing is a later phase)
Full plan and reasoning captured in the project's `05-SIGNUP-SCOPE.md`. Context: Travis wants real Stripe subscription billing (device-count-based pricing, per the direction agreed below), the ability to hand out free/comped accounts, and a basic affiliate program — but rather than block signup on all of that being built, the agreed approach is **free signup now, billing and the affiliate payout ledger as later phases**, since someone was ready to sign up and waiting on the full billing build wasn't worth the delay for a feature that doesn't charge anyone yet anyway.

- **New `signup.html`** (also reachable at the clean URL `bribetheband.live/signup` — see Domains above): collects display name, handle (live-validated — see Performer handle rules above), email, password, and an optional promo/referral code. No payment step at all in this phase.

- **Account creation via a database trigger, not a client-side insert — and why**: rather than the browser calling `auth.signUp()` and then separately inserting a `performers` row (which can hit a real RLS/timing problem — a brand-new signup may have no active session yet, e.g. if Supabase's "confirm email" setting is on), a Postgres trigger (`handle_new_performer_signup()`, `security definer`, same pattern as `get_song_request_status`) fires `after insert on auth.users` and creates the matching `performers` row itself, reading `handle`/`display_name`/`promo_code` out of the signup call's `user_metadata` (passed via `signUp({..., options: {data: {...}}})`). This sidesteps RLS/session-timing entirely, since the trigger runs with its own privileges regardless of whether the new user has an active session yet.

- **One unified `promo_codes` mechanism, not three separate systems** — directly from Travis's own framing: "a discount code feature could be used in conjunction with an affiliate... also use the discount code to give a free account when I need to." A single code can carry any combination of: `grants_free_account` (permanently comps the signer-upper's account — sets their `plan_status` to `'comp_free'`), a customer-facing `discount_percent`/`discount_months` (applied whenever a real Stripe subscription eventually gets created for them — nothing to apply yet, since billing doesn't exist), and separately, an `affiliate_commission_percent`/`affiliate_commission_months` (what the code's owner — the affiliate — earns from anyone who signs up with it, once real billing exists to compute a share of). Discount duration and commission duration both support the same "perpetuity vs. a predetermined timeframe" choice Travis asked for — a null `_months` value means "forever," a number means "only for their first N billed months."

- **Codes are Travis-managed, not self-serve** — per his explicit answer: "I will manually set them up." No application/approval flow exists; Travis creates a row in `promo_codes` directly (see the example inserts at the bottom of `migration-signup-v1.sql`) whenever he strikes a deal with an affiliate or wants to comp someone.

- **A link OR a typed code both work** — per Travis's ask ("I will need to be able to give them a link and/or code"): `signup.html` reads `?ref=CODE` or `?code=CODE` from its URL and pre-fills/auto-validates the promo field, so an affiliate link like `bribetheband.live/signup?ref=SOMEBAND15` behaves identically to someone typing `SOMEBAND15` in by hand.

- **Live promo-code validation via a SECURITY DEFINER function (`validate_promo_code`), not a direct table read**: affiliate commission terms are Travis's own business arrangement with that affiliate, not something the person redeeming the code should be able to read by querying `promo_codes` directly — so that table has RLS enabled with no anon-readable policies at all, and the function only ever returns the four customer-facing fields (valid, grants_free_account, discount_percent, discount_months) plus a friendly message, never the affiliate commission fields.

- **`plan_status` distinguishes three states going forward**: `'free_beta'` (the default for any normal signup right now, before billing exists — nobody's account should be silently auto-converted to paid once billing launches without Travis explicitly doing so), `'comp_free'` (a promo code granted a permanent free account), and (once billing exists) a real paying status. Added specifically so today's free signups stay distinguishable later, rather than being ambiguous with a future real free tier.

- **Explicitly NOT built in this phase** (see 05-SIGNUP-SCOPE.md for the full reasoning): any actual Stripe billing/subscription creation; any real money movement for affiliates (the `affiliate_commission_*` fields on `promo_codes` are recorded now so nothing is lost, but there's no report yet computing "$ owed to affiliate X" — that needs real Stripe charges to exist to compute a share of, so it's a phase that follows billing, not one that can be built ahead of it); Stripe Connect or any other automated-payout infrastructure — Travis explicitly chose a simple tracked ledger he pays out from manually over automated splits, to avoid the real complexity (per-affiliate identity verification, tax-form thresholds, a much larger compliance surface) of Stripe Connect for what's currently a one-person-run app; any device-count enforcement (nothing today actually stops unlimited `viewer.html?role=follower` tabs — this is a real open question for whenever billing/device-tier enforcement gets built, not resolved here).

- **`vercel.json` updated**: an explicit `{"source": "/signup", "destination": "/signup.html"}` rewrite, placed before the generic `/:handle` catch-all (first match wins), so the clean affiliate-shareable URL works.

## Chart storage: Wasabi (S3-compatible) — now fully writable/deletable from the app, one consistent folder scheme
- **Bucket: `songchart` (singular), region `us-east-1`.**
- **Key structure: `charts/{performer-id}/{song-id}.pdf`** — keyed off the performer's immutable internal database ID, not their (potentially-changeable) handle. This was a deliberate choice Travis confirmed: "will make organization and recognition much easier," and it means chart links never break if a handle is ever changed later.
- **Historical note, now fully resolved:** the original 50 seed songs were uploaded manually, before the console existed, into a *handle*-based folder (`charts/travis-ross/...`) — inconsistent with the ID-based folder every upload/replace/delete function has used since. This surfaced when Travis replaced a few charts through the console (Wonderwall, Yellow, A Long December, Hey There Delilah) and noticed the replacements landed in a different-looking folder than the originals.
  - **First fix attempt (had a real bug):** a temporary serverless function (`api/migrate-legacy-charts.js`) listed everything under the old handle-based prefix, copied each file into the ID-based folder (skipping any song already replaced), and was supposed to update `songs.chart_url` to the new path before deleting the old file. The Wasabi copy/delete steps worked correctly — but the function's Supabase client was never given the caller's auth token (it only used the token to verify identity via `auth.getUser()`, never attached it to the client's own requests), so every `songs` table UPDATE it issued ran as an unauthenticated request. The database's row-level security silently allowed the request to "succeed" while actually updating zero rows — no error was raised, so nothing in the migration's own reporting caught it. Net effect: files were correctly relocated in Wasabi, but most of the ~46 migrated songs kept pointing at their old (now-deleted) URL in the database, surfacing later as "missing chart" errors in the new chart viewer.
  - **Actual fix:** a one-time SQL statement, run directly in Supabase, rewrote every song's `chart_url` still matching the old path pattern to the correct ID-based URL (no re-copying needed — the files were already sitting correctly in Wasabi from the first attempt): `update songs set chart_url = 'https://s3.us-east-1.wasabisys.com/songchart/charts/' || performer_id::text || '/' || id || '.pdf' where chart_url like '%/charts/travis-ross/%.pdf';`. Confirmed working afterward.
  - **Lesson for any future server-side write via one of these functions:** a Supabase client created with just the anon key does not carry the calling user's identity into RLS-protected writes, even after calling `auth.getUser(token)` to verify who they are — that only validates the token, it doesn't attach it to the client's outgoing requests. Writing as the authenticated user requires constructing the client with the token attached (`createClient(url, anonKey, { global: { headers: { Authorization: 'Bearer ' + token } } })`), or using a service-role key scoped intentionally to bypass RLS. `wasabi-upload-url.js` and `wasabi-delete-chart.js` were never exposed to this bug because they only ever touch Wasabi directly (using the admin-level Wasabi key, not Supabase RLS) — the actual `songs` table writes for add/replace/delete all happen client-side in the browser, authenticated with the real logged-in session. `migrate-legacy-charts.js` was the one function that tried to write to Supabase itself, and where the bug lived.
  - The old `charts/travis-ross/` prefix is confirmed empty (S3-style storage has no real folders, so an empty prefix simply stops appearing in the file browser). The one-time migration button was removed from `console.html` after use; the function file itself is still in the repo but unused now that all charts share one scheme and one correct set of database links.
- **Public-read via bucket policy, not per-object ACLs:**
  ```json
  {
    "Version": "2012-10-17",
    "Statement": [
      {
        "Sid": "PublicReadCharts",
        "Effect": "Allow",
        "Principal": "*",
        "Action": "s3:GetObject",
        "Resource": "arn:aws:s3:::songchart/*"
      }
    ]
  }
  ```
- **One shared bucket, not per-user buckets.** Multi-tenant storage is handled with a performer-scoped key prefix inside the single `songchart` bucket.
- Every chart's real Wasabi filename is the authoritative Song ID — verified against the actual bucket listing (see `02-SONG-DATABASE.md`) for the original 50, not derived by guessing from the title.
- CORS-enabled so the browser-based viewer (and the console's PDF/ZIP export) can fetch PDFs directly.
- **Direct browser-to-Wasabi uploads**, via a presigned-URL pattern:
  1. The console asks the `api/wasabi-upload-url` serverless function for a short-lived (5-minute) signed upload URL for a specific song slug.
  2. The function verifies the caller's Supabase session token, looks up their `performers` row itself (never trusts a performer id from the client), and signs a URL scoped to `charts/{their-performer-id}/{slug}.pdf` only.
  3. The browser then `PUT`s the file bytes directly to that signed URL — the file never passes through Vercel's function, just the small JSON request/response for the URL itself.
  4. The Wasabi access key used for signing lives only as Vercel environment variables (`WASABI_ACCESS_KEY_ID`, `WASABI_SECRET_ACCESS_KEY`) — never sent to the browser.
- **Direct browser-triggered deletes**, via `api/wasabi-delete-chart.js` — same auth/scoping pattern as upload, issues a `DeleteObjectCommand` for the caller's own `charts/{their-performer-id}/{slug}.pdf`. Triggered automatically when a song is deleted from the console's Manage Songs list.
- **Wasabi credentials: Travis created a dedicated sub-user** (not the root account) with write access to just the `songchart` bucket, following least-privilege practice.
- **Chart replacement reuses the same key/slug**, so a replaced PDF's public URL never changes — the console appends a cache-busting query string (`?v=<timestamp>`) to its own "view PDF" links so a browser tab doesn't show a stale cached copy right after a replace.
- **Deleting a song cleans up fully**: removes the catalog row, deletes the chart PDF from Wasabi, and strips the song's id out of every saved setlist's `song_ids` array.

## User / performer identity model — built in V1, not deferred
- **Internal ID vs. public handle are separate fields, never the same mechanism.** `performers.id` is the app-internal id everything else references (songs, setlists, gig sessions, and now Wasabi storage keys — see Chart storage above). A separate `performers.auth_user_id` column links to the real Supabase Auth account (`auth.users.id`) — kept as a separate column rather than reusing `performers.id` directly, specifically to avoid a data migration across all the already-existing foreign keys pointing at Travis's original seeded `performers.id`.
- **Public handle/display name is user-chosen, not derived from a legal name.** Appears in the crowd-facing URL path (`bribetheband.live/{handle}`) — see Performer handle rules above.
- **Why:** a real name isn't guaranteed unique, isn't stable, exposes PII unnecessarily since chart storage is public-read, and doesn't work at all for a band.
- For Travis today: `travis-ross` is both his handle and (informally) his identity; his `performers.auth_user_id` is linked to a real Supabase Auth account (`travisross@me.com`) created for him. His `performers.email` contact field is separately set to the same address, though the two fields serve different purposes (login identity vs. contact info) and aren't required to match. A second performer row, `travis-ross-test`, exists purely as a standing test sandbox — see Standing test performer account above.
- **Login for the Performer Console: real Supabase Auth (email/password).** Travis's own account and the test account were both created directly via the Supabase dashboard (manual setup, same process each time) — new performers going forward use the self-service `signup.html` instead (see Self-service signup above).

## Data model (current, as actually implemented in Supabase)
- **`performers`**: `id` (uuid, PK), `handle` (unique), `display_name`, `email`, `auth_user_id` (uuid, unique, → `auth.users.id`), `created_at`. `max_requests_per_gig` (the round-1, song-scoped, fixed-forever version of the request cap) **was dropped 2026-08-19** via `migration-drop-legacy-columns-v1.sql`, once a full-repo search confirmed no live code still read it (only old v1/v2 migration files referenced the name, kept as history). **New, added by `migration-signup-v1.sql`**: `plan_status` (text, default `'free_beta'` — see Self-service signup above for the full set of values and what each means), `referral_code` (text, nullable — which `promo_codes.code` this performer signed up with, if any; the affiliate-attribution link), `discount_percent`/`discount_months` (numeric/integer, both nullable — a discount to apply whenever a real Stripe subscription eventually gets created for this performer; null `discount_months` with a set `discount_percent` means the discount is perpetual).
- **`songs`**: `id` (text slug, PK), `performer_id` (→ performers), `title`, `artist`, `song_key`, `key_with_capo`, `chart_url`, `created_at`. (`is_hidden` boolean, default `false`, was added later — see the staging environment doc / recent session work for the hide/delete history-preserving feature that added it.)
- **`setlists`**: `id` (uuid, PK), `performer_id` (→ performers), `name`, `song_ids` (text array, ordered), `created_at`. Multiple can exist per performer; one is chosen as active per gig.
- **`gig_sessions`**: `id` (uuid, PK), `gig_code` (unique, auto-generated by the console, no longer meaningful to the audience URL), `performer_id` (→ performers), `active_setlist_id` (→ setlists), `runtime_order` (text array — now updated live by the request drawer's splicing, not just set once at gig start). `request_cap` (nullable integer — the current, round-3 nightly request cap: one number applied to every song in this gig; carried forward from the previous gig automatically when a new one starts). `cap_reset_at` (nullable timestamptz — when set, only requests created after this moment count toward the cap; the console's "Reset Request Counts" button sets this to `now()` rather than touching any request rows). `status` (`active`/`ended`), `created_at`. **`cooldown_minutes`** (nullable integer, added `migration-queue-cooldown-v1.sql`, 2026-08-27): how long a song stays un-requestable after the performer marks it played; carried forward night to night the same way `request_cap` is. **`display_name_override`** (nullable text, added `migration-display-name-v1.sql`, 2026-08-27): a per-gig override for the name shown on the crowd page (tip prompt + song-list heading), settable in the console's Step 1; falls back to `performers.display_name` when blank. Only one `active` session per performer is meaningful at a time — starting a new gig in the console ends any prior active one and carries forward the previous gig's `request_cap` (and now `cooldown_minutes`/`display_name_override` too). `song_caps` (the round-2, per-song-per-gig jsonb map) **was dropped 2026-08-19** via `migration-drop-legacy-columns-v1.sql`, same reasoning as above. (The earlier-planned `max_plays_per_gig` column was never built — that whole global-plays-cap approach was superseded first by the per-song request cap, then twice more by the two per-gig designs above.)
- **`requests`**: `id` (uuid, PK), `gig_session_id` (→ gig_sessions), `song_id` (nullable — null means a tip-only submission, and later given `on delete set null` so a deleted song doesn't orphan historical requests), `tip_amount`, `note`, `status` (`pending`/`accepted`/`declined`), `queue_position`, `created_at`, **`spliced_at`**: nullable timestamptz, set the moment an accepted request's song is actually inserted into a gig's live page stream (or immediately, for a tip-only "Got it" acknowledgment, since there's nothing to splice). All requests for the same song accepted and spliced together share one `spliced_at` value (see Runtime setlist splicing above) — this is what lets `get_song_request_status()` count them as a single occasion via `count(distinct spliced_at)`. Distinguishes "genuinely accepted, still waiting to be spliced" from "already handled" — necessary once `'accepted'` started being read as a real signal by the viewer, not just a queue-clearing label. **`splice_after_song_id`/`splice_after_page_num`** (nullable, added by `migration-band-sync-v1.sql`): the song+page the Master was viewing at the moment it spliced, used by Follower tablets to find the same insertion point in their own copy of the page stream — see Multi-tablet band sync above; this reference now advances per-song within a multi-song batch (see the bug fix in Runtime setlist splicing above), not just once for the whole batch. **`is_manual`** (boolean, default `false`, added by `migration-manual-add-v1.sql`): marks a row as inserted by the Master's manual-add search tool rather than a real crowd request — excluded from the crowd-facing cap, the viewer's own request badge, and the console's Reporting tab. **`song_title`/`song_artist`/`song_key`** (added in a later session — the denormalization Wade recommended, see Security posture below): a snapshot of the song's identifying info taken at request time, so a song can later be hidden or fully deleted from the catalog without breaking historical reporting or leaving requests pointing at nothing. There is no FK relationship configured between `requests.song_id` and `songs.id` that PostgREST recognizes for embedding — any future query needing both must join them manually in application code (see Request flow above for the bug this caused). `tip_amount` and `note` are also now read directly by `spliceAcceptedRequests()` (see Request-info box above) to populate the performer-facing info box at swipe-arrival, and by the console's Reporting tab to build tip totals. **`stripe_payment_intent_id`** (text, nullable, unique — added by `migration-stripe-v1.sql`, **staging only so far**): set by the Stripe webhook when a paid tip's row gets inserted; the uniqueness constraint is what makes the webhook idempotent against Stripe's at-least-once delivery — see Real Stripe payment integration below. Null for every $0/no-tip row, which is fine since Postgres treats each NULL as distinct for a unique column. **`played_at`** (nullable timestamptz, added `migration-queue-cooldown-v1.sql`, 2026-08-27): stamped only by the viewer's "Got it — play the song" button, never by accepting/splicing alone — this is what starts a song's cooldown (see the dedicated section below) and, separately, what removes it from the crowd page's "in queue" boost strip.
- **`song_plays`**: `id` (uuid, PK), `gig_session_id` (→ gig_sessions, cascade delete), `song_id` (text, → songs, cascade delete), `played_at` (timestamptz, default now()). **Retired/unused** — this table and its RLS policies still exist, but nothing writes to or reads from it anymore, since swipe-based play tracking was replaced by the request cap (see Request-count tracking & nightly request cap above). Left in place rather than dropped, since removing it has no benefit and dropping a table is a one-way action.
- **`promo_codes`** (new, added by `migration-signup-v1.sql`): `code` (text, PK — what gets typed at signup or passed as `?ref=`), `label` (text, nullable — Travis's own note on who/why), `grants_free_account` (boolean, default `false`), `discount_percent`/`discount_months` (the customer-facing discount — see `performers` above for the perpetual-vs-timed convention), `affiliate_commission_percent`/`affiliate_commission_months` (what the code's owner earns from referrals — same perpetual-vs-timed convention, entirely separate from the customer's own discount), `max_redemptions` (nullable — null means unlimited), `redemption_count` (default `0`, incremented by the signup trigger), `active` (default `true`), `created_at`. RLS enabled with no anon-readable `select` policy — validated only through `validate_promo_code()` (see below), never read directly, since affiliate commission terms aren't meant to be publicly queryable.

## SECURITY DEFINER function: `get_song_request_status`
- **Purpose**: lets the anonymous crowd page (`request.html`) find out which songs have hit their nightly request cap, without granting it `select` on the RLS-protected `requests` table (which holds tips and notes that must stay private).
- **Signature (unchanged across all cap-design rounds)**: `get_song_request_status(p_gig_session_id uuid) returns table (song_id text, requests_used integer, max_requests_per_gig integer, is_capped boolean)`. (`song_id` is `text`, matching `songs.id`'s actual type — the v1 function declared it `uuid` and failed with a Postgres return-type-mismatch error the first time Travis ran the SQL; caught and fixed immediately.)
- **Mechanics**: defined `security definer` with `set search_path = public`, so it runs with its owner's privileges (bypassing RLS internally) but only ever returns the four aggregate columns in its signature — no request-level detail (tips, notes, requester info) can leak out through it. `grant execute on function get_song_request_status(uuid) to anon, authenticated;` is the only permission granted — never `select` on the underlying tables.
- **Cap source, by version**: v1 joined `requests` to `songs` and read `songs.max_requests_per_gig`. v2 joined `requests` to `gig_sessions` and read `gs.song_caps ->> r.song_id`. v3 reads `gs.request_cap` directly — the same value for every song in the gig — and additionally filters out any request with `created_at <= gs.cap_reset_at`, so a mid-gig reset zeroes out `requests_used` without touching the underlying rows. v4, in `migration-manual-add-v1.sql`, adds `and not r.is_manual` to both occasion-count expressions so manually-inserted songs never count toward the cap.
- **v5 (current)**, in `migration-queue-cooldown-v1.sql` (2026-08-27), adds four more return columns without changing the meaning of the original four: `queue_tip_total` (running tip sum for a song that's pending or accepted-but-not-yet-played), `in_queue` (true for that same set), `in_cooldown`/`cooldown_seconds_remaining` (derived from `played_at` + `gig_sessions.cooldown_minutes`). A song already `in_queue` is never `is_capped` — boosting an active request bypasses the cap by design, since it's not a new occasion. Adding these required `drop function` before `create function` (Postgres rejects changing a function's return columns via `create or replace`) — see the dedicated feature section below for the full build/port story.
- **Only returns rows for songs with at least one (post-reset) request that gig** — a song with zero requests tonight simply doesn't appear in the result set, which is fine, since "not in the capped set" already means "not capped."
- See `migration-request-cap.sql` (v1), `migration-request-cap-v2.sql` (v2), `migration-request-cap-v3.sql` (v3), `migration-manual-add-v1.sql` (v4), and `migration-queue-cooldown-v1.sql` (v5, current) for the full definitions.

## SECURITY DEFINER function & trigger: `validate_promo_code` and `handle_new_performer_signup`
- **Same pattern, new use**: both defined in `migration-signup-v1.sql`, following the exact `security definer` / `set search_path = public` convention established by `get_song_request_status` above.
- **`validate_promo_code(p_code text)`**: returns `valid`, `grants_free_account`, `discount_percent`, `discount_months`, and a friendly `message` — never the affiliate commission fields. Called live from `signup.html` as the promo field is typed, and once automatically if a code arrived via `?ref=`/`?code=` in the URL.
- **`handle_new_performer_signup()`**: fires `after insert on auth.users`, reads `handle`/`display_name`/`promo_code` from the new user's metadata, looks up and redeems the promo code (if any — validity re-checked here too, not just trusted from the client's earlier check), and inserts the `performers` row itself. See Self-service signup above for the full reasoning on why this is a trigger rather than a client-side insert.

## Row-level security (as implemented)
- Public/anon key: can read `performers`, `songs`, `setlists`, active `gig_sessions`; can insert into `requests`; cannot read other people's `requests`. Can additionally call `get_song_request_status()` (see above) to get capped-song info without reading raw `requests` rows, and `validate_promo_code()` to check a promo code without reading `promo_codes` directly.
- Authenticated performer (via `auth.uid()` matched to `performers.auth_user_id`): can manage (`select`/`insert`/`update`/`delete`) their own `setlists`, their own `gig_sessions` (including live `runtime_order`, `request_cap`, and `cap_reset_at` updates — no separate policy needed for any of these, since they're just more columns on a row the performer can already update), and `requests` tied to their own gig sessions (including the `spliced_at` column).
- **`songs` table policies**: `insert`, `update`, and `delete` scoped to `performer_id = (select id from performers where auth_user_id = auth.uid())`, so a logged-in performer can only manage their own catalog rows.
- **`song_plays` table policies**: `select` and `insert` both scoped via `gig_session_id in (select id from gig_sessions where performer_id = (select id from performers where auth_user_id = auth.uid()))` — still in place, but the table is retired/unused (see Data model above), so these policies are now dormant.
- **`promo_codes`**: RLS enabled, no policies granting anon or authenticated direct `select`/`insert`/`update` — everything goes through `validate_promo_code()` (read) or the `handle_new_performer_signup()` trigger (redemption), both `security definer`. Travis manages rows directly via the Supabase SQL editor (see the example inserts in `migration-signup-v1.sql`), not through any app UI yet.
- **Important gotcha to remember (see Chart storage above for the incident this caused):** these RLS policies only apply correctly when the calling Supabase client actually carries the user's auth token on its requests. `auth.getUser(token)` alone (used to verify who's calling, e.g. in the serverless functions) does NOT attach that identity to subsequent `.from(...)` calls on the same client — a client created with just the anon key still makes anonymous requests unless explicitly configured with `global: { headers: { Authorization: 'Bearer ' + token } } }`.
- **This is also what makes the standing test performer account (see above) work with zero application code changes** — every RLS policy above is scoped by `performer_id`/`auth.uid()`, so a second performer row with its own `auth_user_id` is automatically walled off from the real one everywhere: gigs, requests, reporting, all of it.

## Security posture & Wade's review (2026-08-22) — the standing doctrine for this project
Travis had a trusted senior developer (Wade, who consults for "vibe coders") test the live app and send a real code/security review. His findings, and — more importantly — the reasoning behind them, are now the standing bar for how security gets handled on this project going forward, not a one-time fix list. Captured here so every future session (and every future feature) starts from the same doctrine rather than re-deriving it.

**The core doctrine, in Wade's own terms as Travis relayed them:**
- **The client is never the trust boundary. The database/RLS layer is.** Every place this project has ever gotten security "for free" (the standing test-performer account isolating cleanly, the songs/setlists/gig_sessions row-scoping) worked specifically because the RLS policy — not the JavaScript calling it — enforces the boundary. Anywhere a check exists only in `console.html`/`viewer.html`/`request.html` JS (a grayed-out button, a client-computed value, a field the client happens to always send the same way) must be treated as advisory UX only, never as security, because a direct REST/`curl` call to Supabase bypasses all of it.
- **Never trust a client-supplied identifier.** Every serverless function in `/api` already follows this (look up the caller's own `performers` row server-side from their auth token; never accept a `performer_id` in the request body) — this is the pattern to keep using for anything new.
- **Grants and RLS policies are the actual security surface, and they need to be verified, not assumed.** This project's RLS policies were all set up ad hoc in the Supabase dashboard and were never captured in a tracked migration file — meaning "what's actually enforced in prod" has only ever lived in tribal memory, not in git. `migration-security-hardening-v1.sql` (2026-08-22) is the first attempt at making the repo the source of truth for this, and it should be treated as a living file: any future RLS/grant change belongs in a new migration file, and a `pg_policies`/`information_schema.column_privileges` check should be run and reconciled against what's tracked before considering an RLS change "done." **`staging-schema-baseline-v1.sql` (2026-08-25) went further — the FULL schema, for the first time ever, as one tracked from-scratch file** (see the staging environment doc, `07-STAGING-ENVIRONMENT-SETUP.md`).
- **Denormalize when it protects both integrity and reporting — don't just block the "unsafe" action.** Wade's specific example: for a song that's been requested, his preferred fix isn't to simply block deletion (which punishes the performer for a data-model gap) but to snapshot the song's identifying info (title/artist/key) onto the `requests` row at request time, so a song can be deleted from the catalog later without breaking historical reporting or leaving an orphaned foreign key. **This was built** — see `song_title`/`song_artist`/`song_key` in the Data model section above, alongside a separate `is_hidden` toggle on `songs` so a performer has both options (hide from the request page, or fully delete with history preserved). Prefer this shape — copy what a "point in time" record needs onto that record, rather than either blocking a legitimate action or leaving referential integrity to chance — for any future feature with the same tension.
- **Payments-integration testing needs a real environment, not hope.** Wade's stated plan is to keep running his own tests through the Stripe integration work. **Decided 2026-08-25: a dedicated staging/test environment**, not a production payment-bypass mode — see `07-STAGING-ENVIRONMENT-SETUP.md`. **Built, and the real payment integration itself has since been built and verified on it (2026-08-26)** — see Real Stripe payment integration below.

**What Wade's 2026-08-22 review found, and current status of each:**
1. **Cross-performer chart-deletion risk (his finding).** **Fixed**: `migration-security-hardening-v1.sql` re-asserts the `songs` insert/update/delete policies explicitly and idempotently, so this is now version-controlled and re-runnable, with a diagnostic query included to confirm what's actually live before/after.
2. **Data-integrity bug when deleting a song that's been requested.** **Built** — see the denormalization bullet above (`song_title`/`song_artist`/`song_key` snapshot columns plus a separate `is_hidden` toggle).
3. **World-readable PII/billing fields on `performers`.** **Fixed**: `migration-security-hardening-v1.sql` revokes broad table `select` from `anon`/`authenticated` and re-grants only the four public-safe columns at the Postgres GRANT layer (column-level, unlike RLS) — matches exactly what the app already uses, breaks nothing. (A follow-up fix, `migration-fix-performers-grant-v1.sql`, additionally grants `select (auth_user_id)` to `authenticated` only — needed because Postgres requires column-read access for any column referenced in a `.eq()` filter, not just returned columns; this had briefly broken login lookups.)
4. **Bulk-upload silent-failure bug.** Root-caused and fixed earlier this project: a global (non-performer-scoped) `songs.id` primary key was colliding across performer accounts on common cover-song titles (`performerScopedSlug()` fix), and a follow-on same-title duplicate-on-retry bug was separately fixed with a duplicate-skip guard in the bulk-upload flow.
5. **Client-trusted `status` field on `requests` insert.** **Fixed**: `migration-security-hardening-v1.sql` replaces the public insert policy on `requests` with one that requires `status = 'pending'`, `spliced_at is null`, and `is_manual = false`. **A real regression from this fix was found and fixed 2026-08-25** — the strict policy had been applied to both `anon` AND `authenticated`, which silently broke the Master-only manual-add-a-song tool in `viewer.html` (it needs to insert with `status: 'accepted'`). Fixed via `migration-fix-requests-insert-v1.sql`, splitting back into an anon-only strict policy and a separate authenticated policy scoped to the performer's own gig sessions.
6. **Nightly per-song request cap was UI-only.** **Fixed**: a `before insert` trigger (`enforce_request_cap()`) now rejects an insert for a song that `get_song_request_status()` already reports as capped — reusing the exact same function `request.html` calls, rather than a second, potentially-drifting definition of "capped."

**Open items, not yet built (flagged, not forgotten):**
- **UI for deleting a saved setlist and explicitly ending a gig.** Both already work as direct database operations; there's just no button for either in the console yet.
- ~~A payments-testing environment~~ — **done**, see `07-STAGING-ENVIRONMENT-SETUP.md`. The real Stripe payment integration itself has also now been built and verified on it — see below. The equivalent for **production** is still open.
- **Custom SMTP before launch** — already tracked as V2-BACKLOG item 7, now explicitly flagged there as a pre-launch blocker (not just a nice-to-have), per Wade's warning that Supabase's built-in email sender's rate limit is meant for low-volume/dev use and will not hold up once real signups start.

## Real Stripe payment integration — built and verified 2026-08-26 on staging, rolled out to production 2026-08-27
Direct resolution of the "payments-integration testing needs a real environment" doctrine item above. Travis provided real Stripe test-mode keys mid-session specifically to build this. Asked to choose between Stripe's hosted Checkout page or an inline Payment Element, **Travis chose Payment Element** — the customer's card entry stays on the same page rather than redirecting to a separate hosted page, the lower-friction choice for a live-show audience tipping from their phone. (This is a real, deliberate departure from the V2-backlog item's original phrasing, which had assumed a Checkout session — Apple Pay/Google Pay show up automatically in the Payment Element too, so nothing about wallet support was lost by the change.)

**Core design principle, matching the "client is never the trust boundary" doctrine above**: nothing is ever written to `requests` at PaymentIntent-creation time — only a webhook, firing on Stripe's own `payment_intent.succeeded` event, writes the row. An abandoned or failed payment simply never produces a row, so there's no cleanup/expiry logic needed for incomplete payments, and a client can never talk its way into a written row without Stripe itself having actually confirmed the charge.

- **`api/create-payment-intent.js`** (new, no auth — the crowd is anonymous, same privilege level the existing direct `requests` insert already has): re-verifies the gig session is real/active via a fresh query, and **re-runs the exact same `get_song_request_status` cap-check RPC server-side** right before creating a charge — reuse of the single source of truth described above, not a second/potentially-drifting definition of "capped," closing the gap where a client-side-only check could be stale by the time a payment redirect (or, now, an inline confirmation) completes. Enforces Stripe's real $0.50 minimum charge (the existing client-side check only required `>0`) and a $500 sanity ceiling against a fat-fingered custom tip. Uses explicit `payment_method_types: ['card']` rather than Stripe's "automatic" method selection, so every payment method that can appear confirms synchronously — Apple Pay/Google Pay still surface automatically in the Payment Element regardless, since they ride card rails under the hood.
- **`api/stripe-webhook.js`** (new): verifies the Stripe signature (`stripe.webhooks.constructEvent`, needs the raw request body — `export const config = { api: { bodyParser: false } }`), then inserts the request row using the **plain anon key** — deliberately not the more powerful service_role key, since the anon key already has exactly the insert privilege this needs (matching the crowd's own existing browser-side insert). **Idempotent** against Stripe's at-least-once webhook delivery via the new `requests.stripe_payment_intent_id` unique column (see Data model above): a retry hits a Postgres unique-violation (`23505`), which the handler treats as "already processed" and acknowledges with 200 rather than erroring or duplicating — confirmed working via an explicit replay test, not just reasoned through.
- **`request.html`**: loads Stripe.js and the publishable key (safe for client-side exposure, unlike the secret key), mounts a Payment Element inline as soon as a paid tip amount is selected (debounced for the custom-amount field), and confirms via `stripe.confirmPayment({elements, confirmParams:{return_url}, redirect:'if_required'})` — the customer stays on-page for the normal card-payment case; only a rare forced 3-D Secure challenge would trigger an actual redirect, handled as a fallback return-trip check. The existing $0/no-tip path (direct insert, no Stripe involved) is completely unchanged.
- **Real bug found and fixed along the way, unrelated to Stripe itself but directly relevant to staging's trustworthiness**: `wasabi-upload-url.js` and `wasabi-delete-chart.js` (see Chart storage above) were hardcoding the **production** Supabase URL/key even on the `staging` branch — meaning any chart upload/delete from the staging console had been silently hitting production's `performers`/`songs` tables this whole time, unnoticed because nobody had exercised those staging functions live before now. Fixed by reading `SUPABASE_URL`/`SUPABASE_ANON_KEY` from environment variables (now set on the staging Vercel project only) with the original hardcoded production values kept as the fallback default — production's own behavior is completely unchanged by this fix. Also **deleted `api/migrate-legacy-charts.js` entirely** rather than just patching it — same bug, already-dead code (its console button was removed a prior session), and it was the one function of the three with Wasabi *delete* permissions, so it was a live, armed, cross-environment delete endpoint with no remaining purpose.
- **Confirmed working end-to-end** with a real Stripe test-card payment, verified two ways: through the actual rendered Payment Element in a live browser, and via a direct Stripe API confirmation (`pm_card_visa`) against the final deployed code (browser automation genuinely cannot type into Stripe's secure cross-origin iframe fields — an intentional anti-fraud protection on Stripe's end, not a gap in this integration). Idempotency separately confirmed by replaying the identical webhook event and verifying no duplicate row was created.
- **Debugging note worth remembering for next time this table needs checking**: `requests` is deliberately unreadable by the anon key — by design, matching `request.html`'s own existing code comment about why the crowd page uses the `get_song_request_status` SECURITY DEFINER RPC instead of a direct select (see above). Querying `requests` with the anon key to check "did this insert actually work" always returns empty regardless of success, which cost real debugging time chasing a non-existent bug before the actual explanation was found. Always verify `requests` table state with the project's **service_role key**.
- **Vercel env vars added** to the staging project: `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, plus `SUPABASE_URL`/`SUPABASE_ANON_KEY` (the Wasabi-functions fix above). The Stripe webhook endpoint was created via the Stripe API directly rather than the Dashboard, pointed at `https://bribe-the-band-staging-three.vercel.app/api/stripe-webhook`, subscribed to `payment_intent.succeeded`.
- **Apple Pay is live**, on both staging and production. Registration turned out simpler than the note below originally assumed — Stripe's current API (`POST /v1/payment_method_domains`) verifies a domain in one call with no file-hosting step at all. Registered for `bribetheband.live` **and** `www.bribetheband.live` — the apex redirects to `www`, so both had to be registered since Apple Pay validates against whatever origin the browser is actually showing. Apple Pay's button only ever renders in Safari (Mac or iOS) — confirmed as expected platform behavior, not a bug, the one time it appeared missing during testing (a non-Safari desktop browser).
- **Rolled out to production 2026-08-27**, one day after the staging build, same-day as a real gig — Wade wasn't available to test first, and Travis made an informed, explicit call to accept that risk given the small expected crowd, after confirming that card data itself is never at risk regardless (Stripe's Payment Element tokenizes it directly in Stripe's own iframe, never touching this app's server, identically in test or live mode). Same code as staging (byte-identical for the two new API files, which already read Supabase config from env vars with production values as the built-in default); `request.html`'s Payment Element changes were re-applied directly onto `main` rather than merging branches, specifically to avoid also pulling over staging's Supabase-URL swap. Live Stripe keys, live webhook (initially pointed at the apex domain, caught and corrected to `www` before it mattered — see the redirect note above), and the production migration all went smoothly. **Two real, pre-existing bugs were found and fixed during this same rollout, unrelated to Stripe itself**, both severe enough to be worth their own doctrine notes:
  1. `wasabi-upload-url.js`/`wasabi-delete-chart.js` never attached the caller's auth token to their own Supabase client (the exact "auth.getUser(token) alone doesn't authenticate the client's other calls" gotcha already documented above under Row-level security) — so despite correctly validating identity, the follow-up `performers` lookup silently ran as `anon` and failed a column-grant check that only ever applied to `authenticated`. Fixed by attaching `Authorization: Bearer <token>` as a global header on the client.
  2. The `gig_sessions` RLS policy "Performers manage own gig sessions" was scoped `to public` instead of `to authenticated` — meaning it was evaluated (and its `performers.auth_user_id` reference permission-checked) even for the anonymous `anon` role, which was never granted that column. **Net effect: any brand-new anonymous visitor loading the crowd page fresh would fail to find the active gig at all** — a real, live, general outage, not something Stripe-specific, only surfaced because the new Stripe validation was the first code path to re-query `gig_sessions` fresh rather than trusting an already-cached client-side value. Fixed by dropping and recreating the policy scoped correctly to `authenticated`.
  
  Both bugs follow the same underlying pattern already called out in this project's security doctrine — a role-scoping mistake on RLS/grants, invisible until the exact code path that exercises it runs. Worth treating "does this exact query path actually get exercised by anything, ever, for the anon role" as a standing question whenever touching RLS on this project, not just at the time a policy is written.

## Queue boosting, post-play cooldown, and performer display-name override — built 2026-08-27, rolled out to production same day
Originated from a separate Claude Cowork conversation (Travis pasted the transcript and a draft migration file into Claude Code). Two real bugs were caught in that draft before running anything, by introspecting the live schema via the Supabase REST API rather than trusting the draft blind: the return-type-change issue described in the `get_song_request_status` v5 note above, and a `song_id uuid` vs. actual `text` type mismatch. See `04-DECISIONS-AND-OPEN-QUESTIONS.md` (2026-08-27 entries) for the full build/verification/production-port narrative — this section is the durable architecture summary, not the play-by-play.

- **Boosting is not a new mechanic** — it's just another `requests` row for a song already `in_queue` (pending or accepted-but-not-yet-played), submitted through the exact same panel/insert path as a fresh request. Unlimited by design (Travis's explicit choice). No new insert logic anywhere.
- **Cooldown starts only when the performer taps "Got it — play the song"** in the viewer (see below) — not at Accept, not at splice. This was Travis's own clarification of the ambiguity Cowork's draft had flagged, matching the existing "Got it" pattern already used for tip-only acknowledgments.
- **Crowd page (`request.html`)**: an always-visible "🔥 Requested Songs In Queue" strip (sorted by tip total, a ⬆️ Boost button per row), a collapsed "Recently Played" section with a live per-song countdown (client-side ticker between polls, corrected by the next poll rather than re-fetched every second), and per-song inline states in the main list (boostable / grayed-out-cooling-down / grayed-out-capped). Poll interval dropped from 30s to 8s to match the "this page should feel alive" intent.
- **`api/create-payment-intent.js`**: the existing pre-charge `is_capped` re-check (see Real Stripe payment integration above) now also rejects an `in_cooldown` song, via the same RPC call already in place — no new round trip.
- **Known, pre-existing, still-open gap**: the crowd page's $0 "no tip" path is a raw anon-key insert into `requests` with only a client-side cap/cooldown check — bypassable via devtools. True of the cap already, before this feature existed; not closed by this work either. Worth a `security definer` wrapper function at some point, not urgent.
- **Performer display-name override**: `gig_sessions.display_name_override`, settable in the console's Step 1 (see below), shown in the crowd page's tip prompt and a new song-list heading ("Here's a list of curated songs that {name} has selected for you to request.") — not in the page's `<h1>`, which keeps the fixed "Bribe The Band" app branding per Travis's explicit direction. Falls back to `performers.display_name` (existing column, populated at signup) when blank. **Refreshes on the same 8s poll as cap/queue/cooldown status** — an early version only set it once at page load, so a live console edit never reached an already-open crowd tab; fixed same day once Travis caught it during real use.
- **Console (`console.html`) usability pass, same session**: "Step 1 — Go Live" / "Step 2 — Perform" labels above the two main gig-control buttons (Travis found them visually indistinguishable), "Start the Set" relabeled "Start the Set (Open PDF Charts)", and "Start New Gig" switches from primary to secondary button styling once a gig is already live (re-clicking it silently ends the current gig, so it's a rarer, more deliberate action at that point once live).
- **Porting method to production, worth remembering for next time**: not a `git merge staging` (would pull staging's Supabase project and Stripe test-mode key into production) — a diff of `staging` against its own pre-session state, applied as a standalone patch onto a fresh branch off `main`, with every environment-specific line (Supabase URL/key, Stripe publishable key) explicitly grepped-for and confirmed untouched before pushing. Migrations were run against production *before* the code push, verified via the service_role key; safe to do with the old code still live since the old client only reads a subset of the RPC's return columns.
- **Confirmed working in a real gig that same night** — real crowd, real tip-boosted requests, no issues reported.

## Chart Viewer (`viewer.html`) — Stage 2, both phases now built, the ONLY surface used live
Single static file, opens in a new tab from the console's "Start the Set" button. On load: confirms the performer is logged in (same Supabase session as the console, since both are same-origin and the JS SDK persists the session in `localStorage`), fetches the active gig and its `runtime_order`, loads the corresponding song rows, and builds one flat page stream across every song's chart PDF (via `pdf.js`).
- **Navigation**: see the "Swipe/tap navigation" section above for the full, pointer-type-aware input model (touch swipe/tap vs. mouse click-zones vs. arrow keys). No separate "next song" control — it's all one continuous stream, matching the linear page-stream design.
- **Request-count badge, not play tracking**: the header shows "requested Nx tonight" for whatever song is currently on screen, driven by a raw (non-deduped) count of that song's `pending`/`accepted` requests, excluding manual adds — see Request-count tracking & nightly request cap above for the full design and why swipe-based play tracking was retired.
- **Live request drawer and runtime splicing** — Master only: see the "Request flow" and "Runtime setlist splicing" sections above for the full build — a count-only notification badge, a drawer for accepting/declining, and songs spliced into the running order (deduped by song, one occasion per batch) right after the current page once the drawer closes.
- **Request-info box on arrival**: see the "Request-info box on swipe-arrival" section above — a separate, dismissible centered overlay (distinct from the drawer) that shows tip/note detail for a just-spliced song exactly once, the first time the performer swipes onto it. Shown on Followers too. **Its "Got it — play the song" button, previously cosmetic-only, now stamps `requests.played_at` on the song's spliced batch (2026-08-27)** — that's what starts the cooldown described in the dedicated feature section above. `spliced_at` had to be threaded through both the Master's and a Follower's splice code paths so the button knows which batch to stamp.
- **Master-only manual-add search tool**: see the section above — search the full catalog, confirm, and it's spliced in and synced to Followers exactly like a real accepted request.
- **Multi-tablet band sync**: see the section above — Master/Follower role via `?role=follower`, Realtime-driven convergence at splice time, with the multi-song ordering bug now fixed.
- **Per-song load failures**: if a chart's PDF can't be fetched (broken/missing link), that song shows an inline error (title + the failing URL) instead of blocking the whole set — the performer can click past it to keep going. Applies the same way to spliced-in requested songs.
- **End of set**: reaching the very last page shows a small screen with the option to loop back to the top of the set or return to the console — or, if new requests get accepted after that point, the drawer closing resumes the set into them automatically (see Runtime setlist splicing above).
- **Exit**: closes the viewer's tab (since it was opened via `window.open` from the console) rather than navigating within it, so the console tab underneath is exactly where it was left.
- **Display-quality fixes** (an earlier round this project, prompted by Travis comparing the viewer against Apple Books on an iPad): HiDPI-correct canvas rendering (`devicePixelRatio`-scaled backing buffer, same CSS-visible size) to fix blur; full-bleed `#stage` with `header`/`footer` as auto-hiding, tap-to-toggle `position: fixed` overlays instead of permanent flex-layout siblings, so the chart can use the whole screen.
- **Known remaining limitation, not fixable from the page itself**: when using Safari's actual Fullscreen API (the in-page "Full Screen" button), iOS Safari overlays its own non-removable "X" exit control near the top of the screen — that's OS-injected chrome no website can remove. "Add to Home Screen" (the `apple-mobile-web-app-capable` meta tags already added) is the way to get a truly chrome-free launch with no Safari "X" at all.
