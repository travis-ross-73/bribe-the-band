4. ~~Real Stripe-backed payments.~~ **Done — live in production as of 2026-08-27**, not just staging. Built and verified on staging 2026-08-26 (see `07-STAGING-ENVIRONMENT-SETUP.md`), then rolled out to production the very next day (same-day as a real gig, at Travis's explicit request/risk acceptance) with live Stripe keys, a live webhook, and Apple Pay domain verification for `bribetheband.live`/`www.bribetheband.live`. Real backend (two serverless functions) creates a Stripe PaymentIntent and only writes a request to the queue after a webhook confirms payment actually succeeded — never at intent-creation time, so an abandoned payment produces no row. Travis chose an inline **Payment Element** (card entry stays on the same page) over a **Checkout session** redirect, for lower friction during a live show. **Two real, pre-existing production bugs found and fixed during this same rollout, unrelated to Stripe itself**: (1) the Wasabi upload/delete functions never attached the caller's auth token to their Supabase client, so `performers` lookups silently ran as `anon` instead of `authenticated` and always failed column-permission checks; (2) the `gig_sessions` "performers manage own gig sessions" RLS policy was scoped `to public` instead of `to authenticated`, which meant *any* anonymous crowd-page visitor's gig lookup could hit a permission error tied to a `performers` column anon was never granted — a real, active outage for fresh visitors, caught only because the new Stripe code path re-verified the gig session where the old code never had. See `04-DECISIONS-AND-OPEN-QUESTIONS.md` for the full incident writeup. **Apple Pay only renders in Safari** (Mac or iOS) — confirmed as expected behavior, not a bug, when it didn't show in a non-Safari desktop browser during testing.

8. ~~Auto-end a gig session after 12 hours of zero activity.~~ **Done — built and deployed to staging 2026-08-29.** Decided 2026-08-27, surfaced by the multi-tenant question "will 50 performers forgetting to end their gig become a long-term problem?" `check_and_end_stale_gig()` (in `migration-follower-growth-and-autoend-v1.sql`) treats "zero activity" as no new `requests` row since the gig started, and flips the gig to `status = 'ended'` once that's been true for 12+ hours — checked on-poll (piggybacked on the crowd page's existing 8s poll and the console's active-gig load), not a cron job. The "Gigs with zero activity auto-end after 12 hours" copy is live near "Start New Gig" on the console.
