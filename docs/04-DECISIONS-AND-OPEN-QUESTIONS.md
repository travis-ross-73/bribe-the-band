# Decisions Made & Open Questions

## Major update (several sessions ago): architecture pivot beyond the prototype
Travis described a fuller vision for the live-gig experience, which is a real step beyond the artifact-storage prototype in `01-ARCHITECTURE-AND-DATA-MODEL.md`. That file was rewritten to match. Summary of what changed:

- **Single-screen model, not two.** The performer's device runs the entire performer-facing app — song viewer, setlist, and request queue. There is no separate iPhone request-manager app. The iPhone's only job (when needed) is providing a WiFi hotspot so the device has internet at venues with no reliable WiFi.
- **Notification-drawer request flow**:
  - Incoming requests show as a top banner (count only) that never blocks the current chart.
  - Performer opens the drawer on their own timing — no forced interruption.
  - Requests can be accepted one at a time or several in a row; each accepted request queues as an upcoming swipe.
  - The drawer **stays open** until the performer manually closes it, even after accepting multiple.
  - After closing, swiping continues into the newly-queued songs in the order they were accepted.
- **Runtime setlist splicing.** Accepted requests insert into the current gig's live playback order without altering the saved/named setlist.
- **Linear page-stream swipe navigation.** For multi-page charts, swiping moves through *all* pages of the whole set in order. Swiping backward from a song's first page lands on the *last* page of the previous song.
- **Real backend required.** The artifact-storage prototype (`window.storage`) is being replaced with actual infrastructure: a real database, real file storage, and a real hosted domain.
- **Chart storage: Wasabi**, an S3-compatible object storage service Travis already had an account with. Bucket name `songchart` (singular), region `us-east-1`. Public-read via bucket policy, CORS-enabled.
- **Web apps, not native.**
- **No hard deadline.**
- **Hosting costs are low** — likely $0/month beyond domain registration.

## Prior session (round 1): chart viewer display-quality pass — sharper rendering + Apple-Books-style full-bleed chrome
Travis tested the viewer on an iPad and sent screenshots comparing it to reading a PDF in Apple Books: the chart looked "slightly blurry," and even with "Add to Home Screen" removing Safari's own chrome, the viewer's own header/footer bars still kept the chart from feeling maximized — "I would like it to act more like books natively if possible."
- **Blur fixed**: `renderCurrentPage()` in `viewer.html` was sizing the canvas's pixel buffer to the pdf.js viewport in plain CSS pixels, so on a Retina/iPad display (devicePixelRatio 2–3) the browser was stretching a lower-res bitmap to fill the visible area. Now renders at `viewport × window.devicePixelRatio` into the canvas's real pixel buffer while keeping the same on-screen CSS size, with a matching `transform` passed to `page.render()` — the standard pdf.js HiDPI pattern.
- **Full-bleed chrome, Apple-Books-style**: `#stage` now fills the entire viewport (it was previously squeezed between permanent header/footer bars in a flex column); `header`/`footer` became `position: fixed` translucent overlays instead. They auto-hide about 3 seconds after appearing, and (in this first version) a tap in the untouched gap between the existing left/right page-turn zones toggled them back on or off — mirroring Apple Books' tap-the-middle-of-the-page behavior.
- **Fullscreen guidance, unchanged but worth restating to Travis**: Safari's own in-page Fullscreen API (the "⛶ Full Screen" button) always shows its own non-removable exit "X" near the top of the screen on iOS — that's Safari's own UI, not something any website can remove. "Add to Home Screen" (already set up via the `apple-mobile-web-app-capable` meta tags) is the way to get a truly chrome-free launch with no Safari "X" at all.

## Prior session: live request drawer + runtime splicing built (Stage 2, phase 2) — and a real status-value collision found and fixed
Travis said "Let's move onto the next item then - the drawer when a request comes in." Built the full design from the original architecture pivot: count-only badge, drawer that stays open across multiple accepts, splicing on close.
- **`viewer.html` additions**: a small 🔔-plus-count badge, fixed on screen independent of the header/footer chrome (visible even while that auto-hides, or on the end-of-set screen); hidden entirely at zero pending. Tapping it opens a bottom-sheet drawer listing every pending request (same tip-ranked ordering as the console), each with the song's key, note, tip, and a chart link, and Accept/Decline buttons (or a single "Got it" for a tip with no song attached). The drawer only closes on an explicit "Done" tap, not a backdrop click — deliberate, to avoid an accidental close mid-decision live on stage.
- **First version used a 15-second poll**, not a Supabase realtime channel — chosen as the simpler, more predictable option for something running live on stage. This version had a real bug (see next session's entry) that made it appear not to work at all.
- **Splicing deferred to drawer-close, not immediate on Accept**: closing the drawer (`spliceAcceptedRequests()`) picks up every request marked `accepted` but not yet `spliced_at`, loads each song's chart the same way the initial page stream does (including the same inline-error handling for a broken chart), and inserts all of them consecutively right after the page currently on screen, in the order they were accepted (approximated by request creation time, since there's no separate acceptance timestamp — a reasonable simplification given expected volume). The updated running order is written back to `gig_sessions.runtime_order` so it survives a reload. If the set had already reached its end screen, accepting new songs and closing the drawer resumes playback into them automatically rather than leaving the performer stuck on the end screen.
- **Status-value collision found and fixed**: the console's "Dismiss" button has always set a request's `status` to `'accepted'`, purely to clear it from the pending list — that was harmless before, since nothing downstream ever read the value. Now that the viewer treats `'accepted'` as "splice this song into the set," an unrelated console Dismiss would have accidentally queued a song to play. Fixed two ways: (1) the console's Dismiss now sets `status = 'declined'` instead, restoring the label/value match; (2) added a new `requests.spliced_at` column so the splicing logic can tell "genuinely accepted, still waiting" apart from "already handled," rather than relying on `status` alone. A one-time backfill SQL statement (`update requests set spliced_at = now() where status = 'accepted' and spliced_at is null`) marks every pre-existing `'accepted'` row — all of which, under the old meaning, just meant "previously dismissed" — as already closed out, so none of them get retroactively spliced into a currently-active gig the moment this code goes live.

## Prior session: per-song request-cap replaces swipe/play-based tracking — a genuine architecture reversal (round 1 of the cap redesign)
Travis reported that flipping forward in the viewer to preview upcoming songs, then going back, was inflating the swipe-based play counter — his exact words: "sometimes I'll flip forward to see what the next couple of songs are, and then I'll go back. What that does is add to the counter that we've set up." His proposed fix, confirmed via follow-up questions, **replaces** the earlier "plays-cap, one global number per gig, tied to actual swipe-confirmed performance" decision (see "Prior session: play-limit design confirmed..." above) rather than patching it:
- **Swipe-based play tracking is retired as a load-bearing mechanism.** `recordPlay()` and its two call sites in `viewer.html`'s `goToIndex()` have been removed entirely. The `song_plays` table still exists in the database (harmless, unused) but nothing writes to it anymore. There is no plays-cap, global or otherwise — the whole "count actual performances" approach is dropped.
- **Cap design at the time (round 1, superseded twice since — see below): a per-song, artist-configured, nightly request cap** on `songs.max_requests_per_gig`, set once in the console's Manage Songs screen.
- **Tally basis, confirmed by Travis, still current through every later round**: only `pending` and `accepted`-but-not-yet-spliced requests count toward the cap, and multiple simultaneous requests for the same song collapse into **one occasion** — his exact words: "So if a song is requested by 4 people and is pending, that counts as 1 request. Then I would (likely) accept all 4 at the same time and it would still only count as one request since I'm only going to play the song once for all four people." `spliceAcceptedRequests()` in `viewer.html` groups accepted-and-unspliced rows by `song_id`, splices each unique song into the set exactly once, and stamps every row in that group with the *same* `spliced_at` timestamp (not one timestamp per row) so downstream cap counting sees them as a single occasion.
- **Enforcement, confirmed by Travis, still current through every later round**: "Block new requests for that song by graying our the button and a message saying that it's been requested enough for today or something cute like that." Implemented in `request.html`: the crowd page calls a `get_song_request_status()` RPC after loading the active gig (and again every 30 seconds, and once more right before actually submitting, as a last-second safety check), grays out and disables any song that's hit its cap, and shows an inline "Already requested plenty tonight — try another! 🎶" note instead of the request arrow.
- **Viewer's own badge, confirmed by Travis, still current**: "let's have it track how many times the song has been requested. But this number would be the total times it's been requested, not combined like the audience request page summarizes them." This is a *different*, simpler number from the cap-enforcement count — every individual `pending`+`accepted` request row counts separately (not deduped), purely informational for the performer. **Implementation decisions made to turn the confirmed design into working formulas** (flagging these explicitly since the original design didn't spell out exact numbers):
- **Hard cutoff**: `seconds_remaining <= (songs currently in queue) × avg_minutes_per_song × 60 + buffer_seconds` — a direct translation of the confirmed formula. "Songs in queue" collapses simultaneous requests for the same song into one, same rule the request cap already uses.
- **Soft "Last Call" window**: interpreted "`request_buffer_minutes` doubles as both the safety buffer and the soft-warning window" as *reusing the same number for both purposes*, not *sharing one boundary* — so Last Call shows for one additional buffer-length before the hard cutoff actually fires (i.e., cutoff at `needed + buffer`, Last Call starting at `needed + 2×buffer`). **Worth Travis double-checking this is what he meant** — the alternative reading (both zones share the exact same boundary) would mean no soft-warning lead time at all, which seemed to contradict "soft banner before hard cutoff, not instant binary," so this is the interpretation that made the two design bullets consistent with each other.
- **Songs-remaining estimate** (shown on the crowd page instead of a countdown): computed as *headroom* — how many more average-length songs could fit *beyond* what's already queued, not a raw total. It reaches exactly zero at the same instant the hard cutoff fires (same formula, different unit), so the two signals never contradict each other.
- **Multi-set nights**: `total_sets` is informational/UI-copy only in this v1 — `set_ends_at` always means the end of the *final* set regardless of the number entered, so there's no separate per-set cutoff math and no risk of an early cutoff at a set break. This fully resolves the original worry (Travis's own proposed fix) without needing real break-start/end times, which weren't asked for and would have been a bigger, unrequested scope addition.
- **Late requests are never rejected at the database level** — the design explicitly said "flag distinctly for triage," not "auto-decline," so there's no insert-blocking trigger here at all (unlike the cap/cooldown enforcement built 2026-09-02). A late arrival is accepted completely normally; only the Master's drawer visually flags it (`⏰ Came in after requests closed`), computed by comparing the request's `created_at` against `cutoff_reached_at`.
- **`default_song_minutes` UI placement**: there's no dedicated performer-settings screen yet, so this account-level field lives in the same "Last Call" panel as the per-gig settings, clearly labeled as applying to every gig. Move it if/when a real Settings tab gets built.

44. **"Stage Mode" — inverted chart colors in the viewer, built and ported to production — 2026-09-11.** Travis's own idea: a black-background/white-text option for reading charts in low stage lighting, as a toggle rather than a forced default (some performers/lighting setups will still prefer the plain white page).
    - **Implementation**: a single CSS filter (`invert(1) hue-rotate(180deg)`) toggled on `viewer.html`'s existing chart `<canvas>` — not a PDF re-render, so it's instant and free regardless of chart complexity. The `hue-rotate(180deg)` pairing is the standard "dark mode for images" trick: `invert()` alone would also flip any colored ink's hue (a red highlight would render cyan); adding the hue rotation cancels that flip for chromatic colors while still swapping black-on-white to white-on-black, which is all grayscale luminance.
    - **A new button** ("🌓 Stage Mode") next to the existing Full Screen control in the viewer's header. Preference is remembered via `localStorage`, not saved to the account or gig — deliberately a per-device display setting (whichever tablet, in whatever lighting), not data that should follow a performer to a different device.
    - **Verified end-to-end on staging with a real rendered chart**: temporarily added a test song (Mozilla's own public pdf.js demo PDF, a real multi-column academic paper — plenty of black-on-white body text to invert) to the `demo` account, spliced it into a live gig via the viewer's own "+ Add a Song" search, and confirmed both states render correctly, the toggle button's label/active-state update correctly, and the preference survives a page reload.
